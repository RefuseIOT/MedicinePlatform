## 1 概述

### 1.1 设计目标与输入

本文把需求基线中的 17 个用例、9 个领域类、处方 6 状态 9 迁移转换为可编码、可测试、可部署的设计契约。设计输入为《需求规格说明书》v1.0、非功能需求 NFR-01～NFR-08、S0 代码与前端原型。

### 1.2 设计原则

1. 高内聚、低耦合：按业务能力划分模块，模块内部四层组织。
2. 信息隐藏：模块只通过应用服务或端口暴露能力，不直接访问其他模块的 Mapper。
3. 契约先行：接口路径、DTO、错误码、状态枚举先固定再编码。
4. 状态集中：订单和处方状态迁移封装在领域对象，不散落在 Controller。
5. 审计留痕：审核、撤回、核销、作废等业务动作均生成不可变流转记录。

### 1.3 设计约束

| 编号 | 约束 |
|---|---|
| DC-01 | 采用 Java 21、Spring Boot 3.5、MyBatis、MySQL 8。 |
| DC-02 | 前端采用 Vue 3、Vite、Pinia、Vue Router，前后端通过 REST/JSON 通信。 |
| DC-03 | 单团队、课程周期短，部署节点有限，优先保证一致性与可交付性。 |
| DC-04 | 登录采用 JWT HS256；密码采用 BCrypt；接口实施角色、归属、状态三重鉴权。 |
| DC-05 | Long、BigDecimal 在 JSON 中序列化为字符串，时间统一 ISO 8601。 |
| DC-06 | 核心状态迁移采用事务与乐观锁，冲突返回 409。 |
| DC-07 | 图表以 PlantUML 为唯一源，数据库与 API 文档必须能直接指导实现。 |

## 2 总体设计

### 2.1 体系结构设计

#### 2.1.1 架构决策与选型

依据课件“架构设计应比较候选方案对质量属性和约束的支持程度”的要求，对三个候选方案按 1～5 分评估；权重合计 100%。

| 评价维度 | 权重 | 模块化单体 + 前后端分离 | 微服务 | 服务端渲染分层单体 |
|---|---:|---:|---:|---:|
| 6 人团队开发效率 | 25% | 5 | 2 | 4 |
| 事务一致性 | 20% | 5 | 2 | 5 |
| 部署与调试复杂度 | 20% | 5 | 1 | 4 |
| 模块独立性 | 15% | 4 | 5 | 3 |
| 前端交互与角色工作台 | 10% | 5 | 5 | 2 |
| 后续演进能力 | 10% | 4 | 5 | 2 |
| 加权总分 | 100% | **4.75** | 2.70 | 3.75 |

**结论**：选择“模块化单体 + 前后端分离 + 模块内分层”。它满足课程周期、单机部署、强一致事务和多人并行开发约束；微服务的网络、部署、分布式事务成本与当前规模不匹配。若后期访问量增长，可优先把文件存储、通知或统计模块按端口拆出。

#### 2.1.2 系统逻辑架构

模块依赖包图见 [package-modules.puml](diagrams/package-modules.puml)，模块内分层图见 [package-layers.puml](diagrams/package-layers.puml)。后端划分 `identity`、`catalog`、`consultation`、`prescription`、`pharmacy`、`admin`、`common` 七个模块。每个业务模块采用：

`interfaces → application → domain ← infrastructure`

- `interfaces`：Controller、请求/响应 DTO、参数校验。
- `application`：用例编排、事务边界、权限与幂等。
- `domain`：实体、值对象、状态机、仓储端口、领域规则。
- `infrastructure`：MyBatis Mapper、仓储实现、文件与安全适配器。
- `common`：统一响应、错误码、安全上下文、通用配置；不得依赖业务模块。

跨模块规则：问诊模块只保存处方 ID，不直接操作处方表；处方模块通过查询端口读取订单与药品；跨模块写操作由应用服务编排并在单体事务内提交。

#### 2.1.3 系统物理架构

部署图见 [deployment.puml](diagrams/deployment.puml)。浏览器访问 Nginx；Nginx 托管 Vue 静态文件并将 `/api` 反向代理到 Spring Boot；后端访问 MySQL 和本地文件卷。开发环境允许 Vite 代理后端，生产/演示环境使用 Docker Compose 单机部署。

#### 2.1.5 控制模型与运行时

系统主体采用同步“调用-返回”控制模型；登录、下单、接诊、审方、核销均在一次请求内返回确定结果。过期订单与处方采用 `@Scheduled` 定时任务触发。领域内写操作一个应用服务方法对应一个事务；文件先校验并写临时区，业务提交成功后转正式区。并发修改使用 `version` 乐观锁。

图源位于 `docs/02-design/diagrams/`。鲁棒图遵守：参与者只连接边界类；边界类不能直接访问实体；实体之间不承担流程控制。

#### 3.1.1 UC-02 账号维护

- **参与者**：管理员。
- **前置条件**：管理员已登录且账号有效。
- **设计对象**：`AccountController` 接收创建、启停和重置密码请求；`AccountAppService` 校验角色、手机号唯一性并控制事务；`UserRepository` 持久化用户；创建医生时同时建立 `DoctorProfile`。
- **主流程**：管理员填写账号信息 → 系统校验手机号与角色 → BCrypt 加密初始密码 → 保存账号及医生档案 → 返回账号摘要。
- **异常流程**：手机号已存在返回 40902；角色不属于可创建范围返回 40002；目标账号不存在返回 40401。管理员不能停用自己的当前账号。
- **事务边界**：用户和医生档案必须在同一事务中成功或回滚。

#### 3.1.2 UC-06 支付问诊费

- **参与者**：患者。
- **前置条件**：订单属于当前患者，状态为 `PENDING_PAYMENT`，且创建未超过 30 分钟。
- **主流程**：读取订单 → 校验归属和状态 → 使用 BCrypt 校验登录密码 → 以 `status+version` 条件更新为 `PENDING_ACCEPT` → 写入支付时间与操作日志。
- **异常流程**：密码错误返回 40003，订单状态不变并允许重试；订单过期返回 40901；并发支付只有一个请求成功，另一个返回 40903。
- **设计说明**：本项目模拟支付，不接入真实支付渠道，也不新增支付密码字段。

#### 3.1.3 UC-07 接诊与拒诊

- **参与者**：订单指定医生。
- **主流程**：医生从工作列表打开订单；选择接诊时订单进入 `IN_CONSULTATION`；选择拒诊时必须填写理由，订单进入 `CANCELLED` 并将退款状态置为 `PENDING`。
- **权限规则**：非订单医生访问时返回 404，防止泄露订单存在性；管理员仅能查看，不能接诊。
- **并发规则**：医生接诊、拒诊和超时任务同时发生时，以乐观锁最先成功者为准。

#### 3.1.4 UC-10 提交处方审核

- **参与者**：开方医生。
- **前置条件**：处方属于当前医生，状态为 `DRAFT` 或 `REJECTED`。
- **边界对象**：处方编辑页、`PrescriptionController`。
- **控制对象**：`PrescriptionAppService`、`PrescriptionStateMachine`。
- **实体对象**：`Prescription`、`PrescriptionItem`、`Drug`、`PrescriptionFlowRecord`。
- **主流程**：加载处方聚合 → 校验诊断和 1～5 条明细 → 批量确认药品仍启用 → 执行 T1/T5 → 条件更新版本 → 追加流转记录。
- **异常流程**：处方归属不符返回 404；药品停用或明细非法返回 40001；状态不允许返回 40901；版本冲突返回 40903。

#### 3.1.5 UC-11/12 审核处方

- **参与者**：药师。
- **前置条件**：处方状态为 `PENDING_REVIEW`。
- **审核通过**：执行 T3，设置 `validUntil=reviewedAt+3d`，追加 `APPROVED` 流转记录。
- **审核驳回**：理由不少于 10 字，执行 T4，保存理由并追加 `REJECTED` 流转记录。
- **一致性**：处方状态更新和流转记录写入同一事务；任何一步失败都整体回滚。

#### 3.1.6 UC-14 核销处方

- **参与者**：药师。
- **前置条件**：处方处于 `PENDING_DISPENSING` 且当前时间未超过有效期。
- **主流程**：扫描或输入处方号 → 展示患者与药品摘要 → 二次确认 → 执行 T8 → 写入核销人、核销时间与流转记录。
- **异常流程**：已核销、已作废或过期均返回 40901，不重复发药；并发核销通过版本字段保证一次成功。

#### 3.1.7 UC-15 结束问诊

- **参与者**：订单医生。
- **前置条件**：订单为 `IN_CONSULTATION`。
- **业务规则**：若已经创建处方，应完成本次处方提交；若不需要处方，医生必须明确提交 `noPrescription=true`。问诊结束不强制等待处方核销。
- **结果**：订单变为 `COMPLETED`，写入完成时间；问诊消息转为只读。

#### 3.2.2 应用服务与仓储接口

应用服务以一个业务用例为入口，不对外暴露 Mapper。查询服务可组合轻量 DTO；写服务必须加载聚合并调用领域方法。

| 接口 | 代表方法 | 说明 |
|---|---|---|
| UserRepository | `findByPhone()`、`save()`、`updateStatus()` | 账号持久化端口 |
| OrderRepository | `findOwned()`、`updateStatusIfVersion()` | 订单归属查询与条件更新 |
| PrescriptionRepository | `findAggregate()`、`updateIfVersion()` | 同时加载处方及明细 |
| DrugRepository | `findEnabledByIds()`、`save()` | 批量校验避免 N+1 查询 |
| FlowRecordRepository | `append()`、`listByPrescription()` | 只追加的时间线 |

#### 3.2.3 DTO 与领域对象边界

请求 DTO 只承担协议校验，不包含业务状态迁移；响应 DTO 不直接暴露密码摘要、数据库版本以外的内部字段。实体不得依赖 Controller、Servlet 或 MyBatis 注解。Mapper 数据对象与领域对象由仓储实现转换，以防数据库结构直接支配领域设计。

#### 3.3.1 状态迁移伪代码

```text
transition(action, operator, expectedVersion):
    aggregate = repository.findAggregate(id)
    authorize(operator, aggregate)
    target = transitionTable[(aggregate.status, action)]
    if target is null: throw STATE_CONFLICT(40901)
    validateGuard(action, aggregate)
    changed = repository.updateStatusIfVersion(id, target, expectedVersion)
    if changed == 0: throw VERSION_CONFLICT(40903)
    flowRecordRepository.append(action, oldStatus, target, operator)
```

状态更新与流转记录处于同一事务。读取状态后不直接覆盖数据库，而是再次在 SQL 的 `WHERE` 中校验旧状态和版本，避免“先检查后修改”的竞态条件。

#### 3.3.2 定时任务逻辑

- 每分钟扫描超过 30 分钟仍为 `PENDING_PAYMENT` 的订单，分批更新为 `CANCELLED`。
- 每 10 分钟扫描超过 24 小时仍为 `PENDING_ACCEPT` 的订单，取消并进入退款处理。
- 每小时扫描 `PENDING_DISPENSING` 且 `valid_until < now()` 的处方，执行 T9。
- 每批最多处理 100 条，使用状态条件更新保证与在线请求并发安全；单条失败记录日志后继续下一条。

### 3.4 状态机详细设计

#### 3.4.1 处方状态机

| 迁移 | 源状态 → 目标状态 | 角色 | 守卫 | 主要副作用 |
|---|---|---|---|---|
| T1 | DRAFT → PENDING_REVIEW | 开方医生 | 诊断非空；1～5 条有效药品 | 记录提交时间和流转记录 |
| T2 | PENDING_REVIEW → DRAFT | 开方医生 | 药师尚未处理 | 清除当前队列占用，记录撤回 |
| T3 | PENDING_REVIEW → PENDING_DISPENSING | 药师 | 状态与版本匹配 | 有效期 +3 天；写通过记录 |
| T4 | PENDING_REVIEW → REJECTED | 药师 | 理由不少于 10 字 | 写驳回记录 |
| T5 | REJECTED → PENDING_REVIEW | 开方医生 | 再次满足 T1 | 记录重提 |
| T6 | REJECTED → CANCELLED | 开方医生 | 有废弃理由 | 记录作废原因 |
| T7 | DRAFT → CANCELLED | 开方医生 | 有作废理由 | 记录作废原因 |
| T8 | PENDING_DISPENSING → DISPENSED | 药师 | 未超过有效期 | 记录核销人和核销时间 |
| T9 | PENDING_DISPENSING → CANCELLED | 系统 | 当前时间超过有效期 | 记录 EXPIRED |

所有迁移采用 `UPDATE ... WHERE id=? AND status=? AND version=?`；影响行数为 0 时返回 40903。

#### 3.4.2 问诊订单状态机

订单状态图见 [state-order.puml](diagrams/state-order.puml)。该图补足需求阶段只给出状态简表而未完整表达迁移的问题。

## 4 界面设计

### 4.1 页面地图

- 公共：登录、403、404。
- 患者：科室/医生列表、提交订单、待支付订单、问诊室、处方详情。
- 医生：待接诊列表、问诊室、处方编辑、驳回修改、处方详情。
- 药师：药品管理、待审队列、审方详情、待核销队列。
- 管理员：账号管理、统计、操作日志、处方只读详情。

### 4.2 路由和交互约束

路由权限统一使用后端大写角色枚举 `PATIENT/DOCTOR/PHARMACIST/ADMIN`，多角色页面使用 `meta.roles` 数组。列表必须提供加载、空数据、失败与重试状态；破坏性动作使用二次确认；接口返回 401 清除令牌，403 进入无权限页，409 保留页面数据并提示刷新。

### 4.3 关键页面设计

| 页面 | 主要区域 | 输入校验 | 成功/异常反馈 |
|---|---|---|---|
| 登录页 | 手机号、密码、登录按钮 | 手机号格式、密码非空 | 成功按角色跳转；失败保留手机号 |
| 医生列表 | 科室筛选、医生卡片、分页 | 页码和科室 ID | 空数据提示；加载失败可重试 |
| 提交问诊 | 医生摘要、病情描述、费用 | 描述 10～500 字 | 创建后进入支付页 |
| 问诊室 | 订单状态、消息区、输入区 | 文本长度、图片类型和大小 | 结束后输入区禁用 |
| 处方编辑 | 诊断、药品明细、用法用量 | 诊断非空、明细 1～5 条 | 保存草稿或提交审核 |
| 药师审方 | 患者/诊断/明细、通过/驳回 | 驳回理由 ≥10 字 | 操作后返回队列 |
| 核销页面 | 处方摘要、有效期、确认框 | 必须为待核销且未过期 | 成功后按钮禁用 |

前端只把路由守卫作为体验优化，真正权限必须由后端执行。涉及支付、驳回、核销、结束问诊的按钮在提交期间禁用，防止重复点击。

## 5 接口设计

### 5.1 总则

接口基址 `/api/v1`；资源名使用复数名词；查询使用 GET，新建使用 POST，整体替换使用 PUT，局部动作使用语义化子资源。分页参数为 `page`（从 1 开始）与 `size`（默认 20，最大 100）。详细端点见 `docs/03-api/API接口规范.md`。

### 5.2 JSON 序列化

`Long`、`BigDecimal` 输出为字符串；日期时间为带时区 ISO 8601；枚举输出稳定英文编码；请求中的金额禁止浮点运算。

### 5.3 统一响应

```json
{"code":0,"message":"success","data":{},"traceId":"9f25d11be5b84c1a"}
```

204 响应无响应体。`traceId` 由入口过滤器生成并写入 MDC，日志与响应使用同一值。

### 5.4 错误码

| 范围 | 含义 | 示例 |
|---|---|---|
| 400xx | 参数/业务校验 | 40001 参数非法；40003 支付密码错误 |
| 401xx | 未认证 | 40101 token 缺失或失效 |
| 403xx | 角色无权 | 40301 权限不足 |
| 404xx | 不存在或归属不可见 | 40401 资源不存在 |
| 409xx | 状态/并发冲突 | 40901 状态冲突；40903 版本冲突 |
| 500xx | 系统异常 | 50000 内部错误 |

### 5.5 端点清单

端点、DTO、角色和错误码的完整契约见 API 规范。Controller 不包含业务规则，只负责协议转换、参数校验与调用应用服务。

## 6 安全与权限设计

| 控制面 | 设计 |
|---|---|
| 认证 | BCrypt 密码摘要；JWT HS256，有效期 2 小时；日志不记录密码和 token。 |
| 角色 | 接口级角色白名单。 |
| 归属 | 患者只能访问本人数据，医生只能访问本人订单和处方；归属失败返回 404。 |
| 状态 | 动作必须在迁移白名单内，否则 409。 |
| 隐私 | 列表手机号脱敏；图片白名单类型、大小限制、随机文件名。 |
| 审计 | 记录登录、账号维护、支付、接诊、处方状态变化、核销和管理员查询。 |

### 6.1 角色×操作权限矩阵

| 操作 | PATIENT | DOCTOR | PHARMACIST | ADMIN |
|---|:---:|:---:|:---:|:---:|
| 浏览科室/医生 | ✓ | ✓ | ✓ | ✓ |
| 创建、支付本人订单 | ✓ | - | - | - |
| 接诊、拒诊本人订单 | - | ✓ | - | - |
| 发送问诊消息 | 订单本人 | 订单医生 | - | 只读审计 |
| 创建、编辑、提交处方 | - | 开方医生 | - | - |
| 审核处方 | - | - | ✓ | - |
| 核销处方 | - | - | ✓ | - |
| 查看处方 | 本人 | 本人开方/接诊 | 工作需要 | 全部只读 |
| 账号、统计和日志 | - | - | - | ✓ |

### 6.2 字段可见性

| 字段 | 患者 | 医生 | 药师 | 管理员 |
|---|---|---|---|---|
| 患者完整手机号 | 本人 | 脱敏 | 脱敏 | 脱敏 |
| 病情与聊天 | 本人 | 接诊订单 | 不可见 | 默认不可见 |
| 处方诊断/明细 | 本人 | 相关处方 | 审方/核销所需 | 只读、身份脱敏 |

| 操作日志 | 不可见 | 不可见 | 不可见 | 可见但敏感字段过滤 |

### 6.3 文件与 Web 安全

问诊图片只允许 jpg/png/webp，单文件不超过 5 MB，服务端校验真实 MIME、使用 UUID 文件名并经鉴权接口读取；禁止路径穿越。Vue 禁止对用户内容使用 `v-html`，MyBatis 只使用 `#{}` 参数，生产环境前后端同源，不开放宽泛 CORS。

- 用户角色采用单表 + 角色枚举；医生专属属性放 `doctor_profile`，与用户 1:0..1。
- 聚合根一表，值对象展开为列；处方与明细采用 1:N 外键。
- 枚举存英文编码，Java 枚举与数据库 CHECK/应用校验一致。
- 不依赖数据库级联删除；历史交易采用逻辑状态保留。
- 所有查询条件使用参数化 SQL；高频“归属 + 状态 + 时间”建立组合索引。

## 8 部署设计

Docker Compose 包含 `web`（Nginx+前端）、`app`（Spring Boot）、`mysql` 三个服务和 `uploads`、`mysql-data` 两个持久卷。敏感配置由环境变量注入：数据库密码、JWT 密钥、文件目录；健康检查依次为 MySQL、后端 `/actuator/health`、Nginx。生产环境禁止使用默认 JWT 密钥和默认数据库密码。

### 8.1 节点与端口

| 节点 | 内部端口 | 对外暴露 | 说明 |
|---|---:|---:|---|
| Nginx/Web | 80 | 80/443 | 静态资源与 `/api` 反向代理 |
| Spring Boot | 8080 | 默认不直接暴露 | REST 服务与健康检查 |
| MySQL | 3306 | 仅开发环境可选 | 只允许应用网络访问 |

### 8.2 环境变量

| 变量 | 用途 | 要求 |
|---|---|---|
| `SPRING_DATASOURCE_URL` | JDBC 地址 | 指向 Compose 中的 mysql 服务名 |
| `SPRING_DATASOURCE_USERNAME/PASSWORD` | 数据库凭据 | 不写入仓库 |
| `JWT_SECRET` | JWT 签名密钥 | 至少 256 bit，生产环境随机生成 |
| `JWT_EXPIRATION` | token 有效期 | 默认 7200 秒 |
| `FILE_STORAGE_PATH` | 图片存储目录 | 指向持久卷 |
| `SERVER_PORT` | 后端端口 | 默认 8080，开发时可覆盖 |

### 8.3 启动和故障处理

启动顺序为 MySQL 健康 → 后端执行/校验数据库脚本并健康 → Nginx 提供服务。数据库和上传目录使用持久卷，容器重建不丢数据。后端不可用时 Nginx 返回统一服务暂不可用页面；数据库连接失败时后端健康检查失败，不接收业务流量。
